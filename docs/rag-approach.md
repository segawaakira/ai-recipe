# RAG（検索拡張生成）をこのアプリに導入するアプローチ

## RAGとは？

RAG = Retrieval-Augmented Generation（検索拡張生成）

AIに質問する前に、**関連する情報をデータベースから検索して取ってきて、それをAIへのプロンプトに添付する**手法。

AIが「自分の知識だけ」で回答するのではなく、「参考資料付き」で回答するイメージ。

### RAGなし（現在のアプリ）

```
ユーザー: 「鶏もも肉、トマト、玉ねぎでレシピ作って」
    ↓
AI: 自分の学習知識だけで回答を生成
```

### RAGあり

```
ユーザー: 「鶏もも肉、トマト、玉ねぎでレシピ作って」
    ↓
① DBから類似の食材を使った過去レシピを検索  ← ここがRAGの「R」
    ↓
② 検索結果をプロンプトに添付               ← ここがRAGの「A」
    ↓
AI: 参考情報 + 自分の知識で回答を生成        ← ここがRAGの「G」
```

---

## なぜRAGが必要？

| 問題 | RAGによる解決 |
|---|---|
| AIが存在しない料理を作り出す（ハルシネーション） | 実在するレシピを参考にするので正確性が上がる |
| ユーザーの好みの反映が雑（現状は直近10件のレシピ名だけ） | 食材に関連する過去レシピの中身まで参考にできる |
| 過去にどんなレシピを作ったか考慮できない | 似たレシピを検索して重複を避けられる |

## キーワード解説

### エンベディング（Embedding）

テキストを**数値の配列（ベクトル）**に変換したもの。

```
「鶏もも肉のトマト煮込み」 → [0.12, -0.34, 0.56, 0.78, ...]（768個の数値）
「チキンのトマトソース」   → [0.11, -0.33, 0.55, 0.77, ...]（似た数値になる）
「チョコレートケーキ」     → [0.89, 0.45, -0.22, 0.01, ...]（全然違う数値になる）
```

意味が近いテキスト同士は、ベクトルの値も近くなる。
これにより「テキストの意味の近さ」を数値で計算できる。

### ベクトル検索

エンベディング同士の距離を計算して「意味的に似ているもの」を見つける検索方法。

通常のDB検索（SQLのLIKE）は文字の一致しか見ないが、
ベクトル検索なら「鶏もも肉」で検索して「チキン」も見つけられる。

### pgvector

PostgreSQLにベクトル検索機能を追加する拡張。
このアプリはPostgreSQLを使っているので、新しいDBを追加せずに導入できる。

## このアプリへの導入ステップ

### Step 1: pgvectorをセットアップする

PostgreSQLにpgvector拡張を追加する。

```sql
CREATE EXTENSION vector;
```

Recipeテーブルにエンベディングを保存するカラムを追加する。

```
Recipe テーブル
├── id
├── name          （例: "鶏もも肉のトマト煮込み"）
├── content       （レシピ本文）
├── ingredients   （["鶏もも肉", "トマト", "玉ねぎ"]）
├── rating        （ユーザー評価 1〜5）
├── embedding     （★ 新規追加: [0.12, -0.34, ...] 768次元のベクトル）
└── ...
```

### Step 2: レシピ保存時にエンベディングを生成する

レシピを保存するタイミングで、レシピの内容をエンベディングに変換してDBに保存する。

```
レシピ作成時の流れ（変更後）:

1. Geminiがレシピを生成
2. レシピをDBに保存
3. 「レシピ名 + 食材」のテキストをGemini Embedding APIに送る  ← 追加
4. 返ってきたベクトルをembeddingカラムに保存                   ← 追加
```

Gemini Embedding APIは無料枠があるので、小規模なら追加コストなしで使える。

### Step 3: レシピ生成時に類似レシピを検索する

ユーザーが新しいレシピを作るとき、入力された食材で過去レシピを検索する。

```
レシピ生成時の流れ（変更後）:

1. ユーザーが食材を入力（「鶏もも肉, トマト, 玉ねぎ」）
2. 入力食材をエンベディングに変換                             ← 追加
3. DBからベクトルが近い＆高評価のレシピを5件検索               ← 追加
4. 検索結果をプロンプトに含めてGeminiに送る                    ← 変更
5. Geminiが参考情報付きでレシピを生成
```

### Step 4: プロンプトを改修する

現在のプロンプト（一部抜粋）:

```
【ユーザーの好み】
好評: チキンカレー、肉じゃが
不評: 麻婆豆腐
```

変更後のプロンプト:

```
【参考レシピ（ユーザーが高評価したもの）】
1. チキンのトマトクリーム煮（評価: 5）
   材料: 鶏もも肉, トマト缶, 生クリーム, 玉ねぎ
   ポイント: 弱火でじっくり煮込む

2. 鶏肉と野菜のグリル（評価: 4）
   材料: 鶏もも肉, パプリカ, ズッキーニ
   ポイント: オリーブオイルでマリネ

上記の好みの傾向を参考に、新しいレシピを提案してください。
同じレシピは避けてください。
```

レシピ名だけでなく中身まで渡すので、AIがより的確にユーザーの好みを理解できる。

| ファイル | 変更内容 |
|---|---|
| `apps/api/prisma/schema.prisma` | Recipeに`embedding`カラムを追加 |

| `apps/api/src/recipe/recipe.service.ts` | 保存時にエンベディング生成、ベクトル類似検索メソッドを追加 |
| `apps/api/src/gemini/gemini.controller.ts` | レシピ生成フローに類似検索を組み込み |

## まとめ

```
現在の流れ:
  食材入力 → Geminiにそのまま投げる → レシピ生成

RAG化後の流れ:
  食材入力 → 過去レシピをベクトル検索 → 検索結果付きでGeminiに投げる → レシピ生成
```

「検索して、添付して、生成する」の3ステップがRAGの本質。
このアプリでは「過去の高評価レシピ」が検索対象のナレッジベースになる。
